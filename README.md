キーワードを入力してGitHub上のリポジトリを検索することができるWebアプリケーションです。

## 環境構築

依存関係のインストール

```
bun install
```

ビルドしてサーバーを起動

```
bun run build
bun run start
```

storybookの起動

```
bun run storybook
```

APIテストの実行

```
bun test
```

## AIを利用した部分

開発に当たってGitHub Copilotを部分的に使用しています。

- 実装とテストパターンのアドバイス

- 全体的なレビュー

## 設計方針

今回は小規模開発として、開発スピードと将来の拡張性を踏まえて設計しました。

### CSRの採用理由

SWRとの相性を優先し、検索体験の向上を目指しました。

ユーザーの入力とページネーション、SWRの制御をクライアント側で完結できます。

運用時にサーバー側のレンダリングを最小化して、CPUコストを抑えるようにしました。

## ディレクトリ構成について

- `src/app/*`
  - 画面とAPIのルーティングです。

- `src/app/api/*`
  - GitHubAPIからデータを取得するためのAPIエンドポイントです。
  - その他APIエンドポイントが必要であればここに追加します。

- `src/components/*`
  - 表示ロジック中心の再利用コンポーネントです。
  - ページ固有ロジックから分離しています。

- `src/lib/*`
  - 複数箇所で使用する共通ユーティリティをまとめています。

- `src/store/*`
  - 状態管理ライブラリ`zustand`の設定ファイルをまとめています。

- `src/types/*`
  - 型定義ファイルをまとめています。

この分割によって、「データ取得仕様変更」「UI変更」「状態管理変更」を分離して、影響範囲を小さくしています。

## UIの設計について

### コンポーネントについて

今回は開発規模を踏まえて、最小限のコンポーネントのみを分離しています。

過剰な分離を避けて運用コストを下げつつ、可読性を優先しています。

### スタイリングについて

スタイリングはTailwind CSSを採用しています。

スタイルの修正を行う際にコンポーネントファイルの編集のみで完結しやすく、影響範囲を小さくすることができます。

## Route HandlersでのAPIエンドポイント作成理由について

今回はGitHubAPIを直接利用せずに、Next.jsのRoute Handlersを仲介しています。

### 採用理由

**1. GitHub アクセストークンをクライアント側に露出させないため**

GitHubAPIは認証なしでも利用できますが、厳しいレート制限があるため、環境変数でアクセストークンを設定して制限を緩和できます。

アクセストークンをクライアント側に露出させないため、サーバー側で実装しています。

**2. 責務の集約**

外部API呼び出し、リクエスト検証、エラー整形等を集約することでUI側をシンプルに保つことができます。

## ライブラリの採用理由

### SWR

同一キーに対するレスポンスを再利用でき、不要な通信を減らすことができます。

不要な呼び出しの抑制と再検証制御でGitHubAPIのレート制限リスクを下げています。

画面遷移や再描画時にキャッシュ済みデータを使用することができ、体感速度の向上ができます。

### Zustand

今回は小さな開発規模なので、軽量でシンプルな`Zustand`を採用しました。

機能ごとに管理を分割できるため、規模が大きくなった際でも設計ルール（命名規則など）を決め運用することができます。

画面遷移時にインプット内のテキストが消えてしまうため、`Zustand`の`persist`を使用して永続化させています。

これによりユーザー体験を向上させることができます。

## テストについて

### コンポーネント

コンポーネントはStorybookを採用しています。

ロード中の振る舞いや、表示するデータの長さなどのパターンを簡単に確認することができます。

### API

APIのテストはBunのテストランナーを採用しています。

BunのテストランナーはVitestやJestに比べて高速にテストを実行できるため、開発体験の向上ができます。

JestやVitestのような書き方で学習コストも低く、細かな修正を行う際でも素早くテストを行うことができます。

### コンポーネントとAPIの分離によるテストのしやすさ

コンポーネントとAPIを分離することで、独立してテストコードを記述することができます。

チームでの開発時は、開発を分担して運用することができます。

## 工夫した点

入力内容の永続化とSWRのキャッシュを組み合わせることで、ユーザー体験の向上を図りました。

無限スクロールを使用せずに読み込みボタンを使用することで、API呼び出しを最低限にし、GitHubAPIのレート制限リスクを下げました。
